Detailed Description

The MDMM Game logic.

This is the place where logic is run. The logic is basically a state machine, where the states are changed based on the game process.

A typical MDMM game run is like following: (ref. Logic::State)

State Definition Accepted Slots Notes
Logic::BeforeRoundStart The game / round has not yet started yet. Typically due to waiting for preparation of agents. Logic::addPlayer() Logic::removePlayer() Logic::roundStart() When Logic::addPlayer() or Logic::removePlayer() is called, all the upgrades are cleared.
Logic::RpsForAction Rock-Paper-Scissors is requested for actions. This is always the first request per action time. Logic::rpsReply() Logic::requestRpsForAction() is emitted when this state enters, Logic::rpsResult() is emitted when this state exits to report the result.
If result is a tie Logic::RpsForAction re-enters.
If there is only one winner, he / she gets all the action orders and Logic::Action enters.
Else Logic::ActionOrder enters.
Logic::ActionOrder If multiple winners has determined in the Logic::RpsForAction state, then in this action time the winners should determine the action order. Logic::actionOrderReply() Logic::requestActionOrder() is emitted when this state enters.
If multiple agents chose same action order, Logic::RpsForActionOrder enters.
Else the actions are got by the choosers, Logic::actionOrderResult() is emitted and Logic::Action enters.
Logic::RpsForActionOrder If multiple winners chose same action order, request Rock-Paper-Scissors to determine who can actually get the action order. Logic::rpsReply() Logic::requestRpsForActionOrder() is emitted when this state enters, Logic::rpsResult() is emitted when this state exits to report the result.
If result is a tie Logic::RpsForActionOrder re-enters.
If the result is not a tie, but there are multiple winners, Logic::RpsForActionOrder re-enters with only winners are requested.
Else the action order is got by the winner. Then if there are still undetermined action orders, Logic::ActionOrder enters, else Logic::actionOrderResult() is emitted and Logic::Action enters.
Logic::Action Request action then apply the action. Logic::actionReply() When a player die due to an action before his action order, then his action is skipped.
Logic::requestAction() is emitted when this state enters, Logic::actionResult() is emitted then action is applied when this state exits.
If there is less than 1 player alive after an action, the remained actions are discarded, Logic::roundOver() is emitted and round overs.
Logic::Upgrade Request upgrade then apply the upgrade. Logic::upgradeReply() Logic::requestUpgrade() is emitted when this state enters, Logic::upgradeResult() is emitted when this state exits to report the result.
When all upgradable properties reaches maximum value, Logic::gameOver() is emitted and game overs.
Note
The Logic is a synchronous, reply-driven state machine: each requestXxx signal expects a matching xxxReply() slot call, and that reply advances the state machine (possibly emitting further requests) within the same call stack. Some requests are emitted in a loop over players — for example requestUpgrade() is emitted once per player with upgrade points — so a directly-connected slot replies re-entrantly while the loop is still running. This is safe by design: each phase only advances once every expected reply has been collected (the reply handlers count replies and act only when the set is complete), and the emit loops iterate over stable containers that the re-entrant advance does not mutate. A direct connection in a single-threaded setup is therefore equivalent to a queued connection; no particular connection type is required. (The reference implementation in QMdmmNetworking runs Logic on its own thread with queued connections purely for thread marshaling, not because direct connection is unsafe.)

◆ actionOrderReply

bool QMdmmCore::Logic::actionOrderReply ( const QString & playerName,
const QList< int > & desiredOrder )
slot

Receive the desired action order result.

Parameters
playerNamethe internal name of the player
desiredOrderthe desired action order of the player
Returns
true if the reply was accepted and applied as sent; false if it was rejected (unknown player, wrong state, or duplicate) or replaced by a full yield because the order list is invalid (the state machine still advances)

Can be only called from Logic::ActionOrder state.

The reply must contain exactly as many entries as the selections that were requested from the player. Each entry is either an order the player wants to strive for (in range 1..maximumOrderNum, not already confirmed, and not duplicated) or 0 to yield that action opportunity — the player accepts whatever order is left over and stops competing for it. An invalid reply is not rejected: it falls back to yielding every selection, so a buggy or malicious agent cannot stall the ActionOrder phase.
