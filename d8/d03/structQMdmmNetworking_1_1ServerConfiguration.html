Detailed Description

Contains configurations of server.

The configuration is a QJsonObject with well-known keys. Because the class inherits QJsonObject, arbitrary keys can be inserted and values are not validated on access; unknown keys are ignored. Call deserialize() to validate a raw JSON value (rejecting wrong types and out-of-range values) before using it.

Every key here is a start-up setting rather than a per-game one, and a key an operator would change at start-up is reachable three ways: a command-line option, a stored key in the configuration file (named after the option), and a row in doc/command-line.md. The three go together – an option with no stored key is a setting that cannot be remembered between runs, and a key with no row is one nobody can find – and the server's own command-line tests hold the properties declared here to the keys the program stores, so a new key cannot miss them without turning a test red.

There is one shape today and no second one: every property declared here is a start-up setting an operator would tune, so it carries all three faces. A key whose value no operator would tune therefore has nowhere to go while the gate stands as it does – the properties declared here and the keys the program stores are held equal, with nothing subtracted on either side – so adding one means changing that gate in the same commit, not only declaring the property.

bool QMdmmNetworking::ServerConfiguration::deserialize ( const QJsonValue & value)

deserialize QJsonValue to ServerConfiguration

Parameters
valuethe value to be deserialized
Returns
if the deserialize succeeded
Note
It is possible to convert the value to QJsonObject and directly assign the value, since this class inherits QJsonObject, but the value check in this function will be nonexistent then.

The value must be an object. Any absent key falls back to its default value (as returned by defaults()), so a partial or empty object is accepted; a present key must still be valid. Boolean fields must be booleans and string fields must be strings; every numeric field must be a whole number (fractions, NaN and negatives are rejected). Ports must be in [1, 65535] (port 0 is reserved); controlPort is either 0 (the plane is off, which is its default) or such a port; playerNumPerRoom must be at least 2 (a game needs an opponent for rock-paper-scissors action-order resolution); requestTimeout is either 0 (no timeout) or at least 15 seconds; maximumPacketSize is at least 1024 bytes; signInTimeout is between 2 and 60 seconds; maximumRooms is 0 (no limit) or any positive number of rooms. Unknown keys are ignored.

Property Documentation

◆ controlPort

uint16_t QMdmmNetworking::ServerConfiguration::controlPort
readwrite

The port the read-only control plane listens on, default 0 (off).

The control plane is a second, deliberately narrow listener: it speaks HTTP/1.0 on the loopback address only and serves one path, /status, with the same snapshot Server::status() returns. It carries no game traffic and cannot change anything. 0 turns it off, which is the default, so a server that was not asked for one opens no port beyond the transports it was configured with. Port 0 is not "pick one for me": an operator who reads the snapshot has to know where the endpoint is, so the plane is either at a port that was named or not there at all.

◆ requestTimeout

int QMdmmNetworking::ServerConfiguration::requestTimeout
readwrite

The request timeout in seconds, default 20.

The server's request timer only backstops abnormal cases now: a healthy client replies or explicitly gives up on its own, so the timer fires only when the client is gone or stuck. The value is in seconds; it is converted to milliseconds when the request timer is armed, and a non-zero value is extended by a grace period before the connection is treated as gone. A value of 0 turns the request timer off: a request then waits for its reply for as long as the client takes.

Independent of it, every signed-in connection carries a silence deadline of 90 seconds – three times the interval at which a client pings. A peer that sends nothing at all for that long is dropped, and no setting here turns that off. Waiting on a request and keeping a connection alive are two different questions: a request may be waited on indefinitely, while a connection whose peer has stopped speaking is gone whatever is being waited for.

◆ maximumPacketSize

int QMdmmNetworking::ServerConfiguration::maximumPacketSize
readwrite

The largest packet the server accepts from a peer, in bytes, default 1 MiB.

A packet is one line, so a peer that sends this many bytes without ending a line is not speaking the protocol: the server records a Socket::ProtocolError and drops the connection instead of buffering data that can never become a packet. The value has to be at least 1024, so that the protocol's own packets always fit; there is no "unlimited" setting, since the bound is the point.

◆ signInTimeout

int QMdmmNetworking::ServerConfiguration::signInTimeout
readwrite

How long a connection may stay silent before it is given up on, in seconds, default 5.

A peer that connects and never signs in is not a player yet, so nothing else in the server would ever notice it: left to itself, the connection (and the memory behind it) is held for as long as the peer cares to keep the socket open. Every accepted socket is given this long to sign in, and one that has not done so by then is dropped with a Socket::ProtocolError. A connection that did sign in is left alone by this deadline, which is about a peer that never became a player: what watches a player's connection afterwards is the silence deadline described under requestTimeout, and this key does not set it. This deadline is always armed, and a value has to be between 2 and 60 seconds: the upper bound is the one the deadline exists for, keeping a peer that never signs in from holding a port and the memory behind it for longer than a handshake could plausibly take, while the lower bound only has to outlast the slowest honest handshake.

◆ maximumRooms

int QMdmmNetworking::ServerConfiguration::maximumRooms
readwrite

How many rooms the server runs at once, default 0 (no limit).

A room holds playerNumPerRoom players and, once it is full, plays its game to the end in the background while the next room starts recruiting. Nothing else bounds how many of them exist at the same time: a peer that keeps signing in under fresh names can keep building rooms, and each one holds its players and the game it runs for as long as that game lasts. This key is that bound. A sign-in that would need one room more is refused with a Socket::ProtocolError, the way a peer that never signs in is given up on – the room it asked for is not built, so the size the configuration allows is what the server actually holds.

The count is of rooms, not of connections: the connection bound an operator might reach for is derived from this one, since a signed-in peer takes exactly one seat and a room has playerNumPerRoom of them. A player already seated keeps their room, and a player reconnecting signs back into the room they came from rather than asking for a new one, so this key never locks a seated player out. 0, the default, is no bound at all: as many rooms as players ask for, which is what the server did before this key existed.
